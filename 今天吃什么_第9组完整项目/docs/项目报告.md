# 今天吃什么

## 第9组校园就餐推荐系统 · 项目说明与分工报告

版本：1.3.1；更新与测试日期：2026年10月26日。

成员：王俊杰、杨铭宇、李付远、范星宇。

## 一、项目概述

本项目包含原生微信小程序、本地浏览器演示、微信云函数以及测试和说明材料。核心任务是帮助学生了解五个校园餐厅，根据预算、口味和排队信息选餐，并用收藏、评价与众包上报完善公共信息。

浏览器演示双击根目录“一键演示.cmd”即可体验；微信开发者工具导入project.config.json所在目录。当前默认演示模式，云模式需自行配置和验证。

# 二、需求分析

项目名称：今天吃什么；组别：第9组；版本：1.3.1；更新日期：2026年10月26日。

## 2.1 项目背景与目标

学生在校园就餐时，经常面临“不知道吃什么”“不了解菜品价格和口味”“到达食堂后才发现排队较长”等问题。本项目面向校园就餐场景，建设集食堂信息查询、条件筛选、转盘推荐、众包拥挤度、图文评价与收藏于一体的微信小程序，缩短选餐路径，帮助学生作出符合预算和个人偏好的选择。

系统以“浏览与筛选 → 推荐与选择 → 查看排队 → 就餐后评价与上报 → 内容审核”为主要业务闭环。允许未登录用户浏览公共信息；涉及个人记录和数据贡献的操作需要登录。系统不提供支付、外卖配送或陌生人社交功能。

## 2.2 用户角色与权限

| 角色 | 使用目标 | 主要权限与边界 |
| --- | --- | --- |
| 未登录访客 | 快速了解餐厅和菜品 | 查看公开食堂、窗口、菜品、榜单及有效拥挤度；使用筛选和转盘；收藏、上报和评价时引导登录 |
| 学生用户 | 选餐并记录个人体验 | 设置昵称、口味、辣度和忌口；收藏菜品和窗口；上报拥挤度；发布、修改、删除本人评价；举报公开评价；查看本人记录、积分与勋章；主动申请饭点提醒 |
| 管理员 | 保持信息准确与内容可用 | 新增编辑食堂、窗口、菜品，调整价格和上下架状态；审核评价及附图；处理举报；查看统计和操作记录。云端权限由服务端管理员白名单决定 |

学生不能维护公共目录、审批评价、查看其他学生的私人记录或操作他人的评价。管理员权限只用于内容和数据维护，不设置额外的学生社交关系或消费权限。

## 2.4 核心功能需求

| 编号 | 功能 | 具体需求与完成标准 |
| --- | --- | --- |
| F01 | 微信登录与个人设置 | 微信云模式使用服务端识别的微信身份；登录后设置昵称、偏好口味、可接受辣度和忌口。支持退出，退出后清理私人可见状态。拒绝授权或登录失败时提示重试，公共浏览仍可用 |
| F02 | 食堂、窗口、菜品查询 | 五餐厅均有列表入口，可进入窗口及菜品详情。展示名称、所属关系、价格、口味、辣度、荤素、食材标签、在售状态及公开评分；没有评价显示“暂无”，没有菜品显示空状态 |
| F03 | 组合条件筛选 | 按食堂、关键词、价格区间、口味、辣度、荤素和近期排队条件筛选，多个条件同时满足。荤素区分荤食、蛋奶素、纯素；可主动应用个人忌口；支持清空筛选。无结果时提示减少限制 |
| F04 | 随机转盘推荐 | 转盘沿用当前自定义筛选条件，从匹配且在售的菜品中展示最多8道候选，转动结果对应可见扇区。启用口味画像后对偏好口味适当加权，忌口作为硬过滤。多候选时避免连续推荐同一道菜，单候选允许重复；转动期间防止重复触发，结果可进入详情或加入就餐计划 |
| F05 | 众包拥挤度 | 学生可对食堂或窗口上报“较空闲、需等待、较拥挤”。提交后立即刷新；仅聚合最近15分钟的有效上报，同一用户在目标范围内取最新一条，较新的记录权重更高。无有效数据明确显示“暂无上报” |
| F06 | 评分与图文评价 | 登录后可提交1-5星、5-300字、最多3张图片的评价。微信图片为JPG/PNG，每张不超过1MB；浏览器演示支持本地压缩。发布和修改均进入待审核状态；云端完成内容安全检查后，还需管理员人工审核。仅审核通过的评价公开并计入均分 |
| F07 | 菜品与窗口收藏 | 支持收藏、取消收藏；同一用户对同一目标保持唯一收藏效果。收藏状态在列表、详情和个人中心同步；刷新后保留。下架菜品不参加推荐，历史个人记录仍可识别 |
| F08 | 个人中心 | 分类展示“我的评价、我的上报、我的收藏”，显示审核结果、拒绝原因、上报有效状态；可修改本人评价、设置偏好、查看积分和勋章。个人记录只能由本人查看和操作 |

## 2.5 扩展功能需求

| 编号 | 功能 | 具体需求与边界 |
| --- | --- | --- |
| E01 | 饭点订阅提醒 | 用户主动选择午餐11:30或晚餐17:30并申请微信订阅授权；支持关闭。一次授权按一次可发送额度处理，不暗示永久每日提醒。模板、定时器和真实收信需在微信环境验收；本地演示只保存选择 |
| E02 | 三类排行榜 | 人气菜品榜依据累计投票；好评窗口榜依据公开评价均分并展示评价数；拥挤度榜依据近期有效上报。票数并列按价格从高到低保持确定顺序，均分及拥挤等级并列保持目录顺序；无评价或无上报不伪造分数和客流 |
| E03 | 积分与勋章 | 每日首次至第五次有效上报各加2分；每条审核通过的评价加5分。评价被拒绝、删除或修改为待审时撤回对应积分。5、20、50分对应不同勋章，积分从有效记录计算，防止反复审核重复奖励 |
| E04 | 管理端与举报 | 支持食堂、窗口、菜品维护，菜品上下架，评价文字和图片审核，举报驳回或隐藏，待处理筛选、搜索和审计记录。非管理员请求必须由服务端拒绝；拒绝评价应提供原因，帮助学生修改 |
| E05 | 每日投票 | 登录用户按北京时间每天可为一道人气菜品投一票；投票成功后更新榜单和已投状态，重复投票明确提示 |

就餐日历、实际花费打卡、周预算及菜品对比作为已有辅助功能保留。花费由用户手工记录，不连接支付或订单系统。

## 2.6 关键业务规则与异常处理

1. **信息关联**：窗口必须引用有效餐厅，菜品必须引用有效窗口；移动窗口后同步菜品所属餐厅。价格用整数分存储，避免小数累计误差。下架后不参与筛选推荐。
2. **推荐规则**：预算、辣度、荤素和忌口均不得被随机结果突破；口味画像来自用户主动选择，采用可解释规则，不宣称使用训练模型。食材标签仅用于辅助筛选，不能代替现场询问。
3. **拥挤度规则**：食堂聚合本食堂及下属窗口上报；窗口只聚合自身上报；同一用户在同一食堂范围内只取最新一次。记录有效期15分钟，页面每30秒刷新；上报后立即更新。同人同地点60秒内不能再次上报，每日最多20次。
4. **评价状态**：待审核 → 已公开或未通过；公开评价修改后恢复待审核。待审内容不计入评分和积分；作者可查看本人待审内容及结果，其他学生不可查看。旧页面审核凭据失效时要求刷新，防止审批已修改内容。
5. **举报处理**：用户说明具体原因，不能对同一评价重复提交待处理举报。举报本身不直接改变评价状态，管理员确认后可驳回或隐藏，处理行为写入操作记录。
6. **失败反馈**：未登录先引导登录；筛选无结果提示放宽条件；图片过大或审核异常时拒绝发布；网络或云函数失败展示真实错误，不以本地成功替代云端失败；存储失败不覆盖原数据。
7. **目录升级**：本地旧版默认目录自动补充为五餐厅，保留已有评价、收藏、计划和管理员修改。扩展ID与自定义数据冲突时保持原目录，转由管理员手动维护。已部署云环境由管理员主动升级，不能由普通学生触发。

## 2.8 创新点及价值

1. **游戏化转盘推荐**：把预算、口味等条件转化为可选择候选，通过转盘降低决策负担，并保留结果详情和下一步入口。
2. **众包拥挤度**：通过学生上报、用户去重与时间衰减反映近期排队状况；同时展示新鲜度和样本信息，避免把陈旧或单一上报当作可靠客流测量。
3. **可解释口味画像**：依据用户主动设置的偏好、辣度和忌口筛选并加权推荐，说明推荐原因，保护用户对推荐条件的控制权。
4. **贡献激励闭环**：用有上限的上报奖励和审核后评价奖励鼓励贡献，通过内容审核、频率限制和积分回退提高数据质量。

## 三、系统设计与实现

### 3.1 技术结构

原生小程序使用JavaScript、WXML、WXSS；浏览器演示使用HTML、CSS、JavaScript。共享core.js负责筛选、推荐、评价、拥挤度、积分、目录与权限规则；store负责本地存储或云调用。campusApi云函数负责可信微信身份、内容安全检查、数据库事务与隐私裁剪；notifyMeals处理饭点订阅发送。

浏览器与小程序演示模式的数据分别保存在本机，彼此不互通。云模式直接返回真实云调用结果，失败时不降级为本地假成功。

### 3.2 主要数据关系

| 实体 | 主要字段及用途 |
| --- | --- |
| 食堂、窗口、菜品 | id、名称、父级ID；菜品价格为整数分，记录口味、辣度、荤素、食材标签和在售状态 |
| 用户与收藏 | 微信身份、昵称、显式偏好；用户ID、目标类型与目标ID确定收藏 |
| 评价与举报 | 用户、菜品、星级、文字、图片、状态与时间；举报关联评价并记录处理结果 |
| 拥挤度与投票 | 用户、目标、等级、时间；投票按北京时间日期限制，每天一票 |
| 订阅与审计 | 提醒时间、授权额度、发送状态；记录目录、审核和举报操作 |
| 私人就餐计划 | 用户、日期、餐次、菜品快照、打卡状态和手工实际花费 |

目录关联通过业务校验维护；写入采用云端版本检查与事务重试。评价图片经检查后另存服务端冻结目录，防止审核后原图被客户端替换。课程原型读取每个业务集合最多2000条，超过限额明确报错；全量快照结构尚不适合全校高并发直接部署。

### 3.3 五餐厅兼容升级

沿用原c1-c3、w1-w6、d1-d18的ID，避免原收藏、评价与计划失联；补充c4-c5、w7-w10、d19-d30。只替换旧默认餐厅名称及默认示例位置信息，保留管理员已修改数据。自定义扩展ID冲突时不执行部分升级。云端必须由管理员发起升级，普通快照不会注入示例目录。
